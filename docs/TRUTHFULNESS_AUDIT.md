# Truthfulness Audit — Permanent Specification

This document is the permanent methodology and terminology specification for the Truthfulness Intelligence layer of NameOrigin's Project Intelligence Engine (Phase 1C, and any future phase that extends it). It describes *how* truthfulness is measured and classified, independent of any specific run's results — those results live in `/audit/*.json` and `/audit/truthfulness-report.md`, regenerated by `node scripts/audit/run-truthfulness.js`.

## What this audit is, and is not

The Truthfulness Audit answers exactly one question, for every factual-statement mechanism a page generator can produce:

> **When this page makes a factual statement, is that statement backed by real structured data, derived deterministically, honestly disclosed as unknown, or substituted with generic fallback text?**

It is **not**:
- A content quality audit (grammar, tone, usefulness).
- An SEO audit (rankings, meta tags, keyword strategy).
- A hallucination detector in the generative-AI sense — nothing on this site is LLM-generated; every "fallback" here is a hardcoded string chosen by conditional logic in a deterministic Node.js script. The concern is masking, not invention.
- A recommendation engine. It does not propose fixes, prioritize work, or judge whether a fallback is "bad." It only counts.

## Terminology

**Assertion** — one distinct, rendered factual-statement mechanism: a specific piece of code (usually one function, or one clearly-scoped branch within a function) that produces a claim about an entity on a page. An assertion is defined by *what code path produces it*, not by which dataset field it happens to read — the same field can back two different assertions if two different functions render it differently (see "Concept" below).

**Concept** — the claim category an assertion belongs to (meaning, origin, popularity, syllables, ...), independent of which template or generator renders it. One concept can map to multiple assertions across multiple templates, each with its own classification. `audit/assertion-catalog.json` is organized by concept; `audit/truthfulness-matrix.json` is organized by template. Both describe the same underlying assertion list — the grouping differs, the data does not.

**Template** — a page category from Phase 1A (`audit/templates.json`), e.g. `name-detail-page`, `sibling-harmony-page`.

**Fallback marker** — a literal string, verified against real generated HTML, that a generator substitutes when a backing field is empty. The permanent catalog of these lives in `scripts/audit/knowledge-lib.js`'s `FALLBACK_MARKERS` array (started in Phase 1B, extended in Phase 1C, intended to keep growing).

## The four classification states

Every assertion is classified into **exactly one** of four states. There is no fifth state, no partial credit, and no numeric score — the classification is categorical.

| State | Definition | Example from this codebase |
| --- | --- | --- |
| **Supported** | The statement comes directly from a real, populated structured-data field for this specific entity. | `Gender: Boy` ← `data/names.json` |
| **Computed** | The statement is derived deterministically from other fields or the entity's own identity, with no possible "missing" state — it is always reproducible. | First-letter grouping, syllable count, spelling variants, a compatibility/harmony score |
| **Disclosed-missing** | The page either states outright that a value is unavailable, or silently omits the section — no specific claim is made in either case. | The Quick Facts table showing `—` for meaning; the Pronunciation section never rendering because `phonetic` is 0% populated |
| **Fallback** | The generator substitutes a generic phrase that reads as a specific, researched claim about this particular entity, when in fact no such research exists for it. | `"{Name} means 'a documented given name'"` when `meaning` is empty |

### Why "computed" is not "supported"

A field can be technically present in a dataset and still be classified `computed` rather than `supported`, if it is a deterministic transform of the entity's own identity (its name string) rather than an independently-researched fact. `first_letter` and spelling `variants` are both stored in JSON files, but neither could ever be "missing" — they are 100% reproducible from the name string alone. `meaning` and `origin_country`, by contrast, require external research and genuinely can be (and overwhelmingly are) absent. This distinction is what makes `computed` assertions immune to the sparsity problem that `supported` assertions are exposed to.

### Why "disclosed-missing" counts as truthful

A page that shows `—` or omits a section entirely is not asserting anything false. It is choosing not to claim. Per this audit's rules, that is truthful behavior, even though it may still represent an information *gap* from a content-completeness point of view (a different question, out of scope here — see Phase 1B's Knowledge Coverage Audit for that lens).

### Why "fallback" is the one negative-signal state

`fallback` is the only state where the rendered text itself is potentially misleading: it reads as if it were specific to the entity ("means 'a documented given name'", "of multiple traditions origin") when it is in fact a generic substitute chosen because no real data existed. This is the mechanism this audit exists to surface.

## Methodology

1. **Reuse before rebuilding.** This phase imports and extends, rather than reimplements:
   - `scripts/audit/knowledge-lib.js` — `FALLBACK_MARKERS` (the literal-string catalog) and `countFilesContainingMarker()` (the scanning function), both introduced in Phase 1B and extended in Phase 1C with newly-discovered mechanisms.
   - `audit/templates.json`, `audit/page-knowledge-matrix.json`, `audit/knowledge-dependencies.json`, `audit/empty-knowledge.json` (Phase 1A/1B) — read back in wherever they already establish a fact (template lists, dataset coverage percentages, dataset→generator chains) rather than recomputing it.
   - `scripts/audit/truthfulness-lib.js` is the one new module: it defines the full assertion list (`buildAssertions()`), each entry computed at run time, not hardcoded as a static percentage.

2. **Every classification is either grep-verified or source-verified, and says which.** Each assertion's `evidence.method` field states how its page count was established:
   - `grep-verified` — counted directly against currently-generated HTML via `countFilesContainingMarker()`.
   - `live-data-count` — counted directly from a `/data/*.json` file at run time.
   - `phase1b-coverage` — pulled from `audit/knowledge-coverage.json`, itself computed the same way in Phase 1B.
   - `source-verified` (only) — the mechanism's *behavior* was confirmed by reading the generator source, but an exact page count could not be established from committed data (see Limitations).

3. **Dominant-state resolution for data-dependent assertions.** Where an assertion behaves differently depending on whether its backing field is present (e.g. `meaning` is `fallback` when empty, `supported` when present), `audit/truthfulness-matrix.json` records the **dominant** (majority, real-world) state as that assertion's single classification, and records the minority behavior in a `minorityPath` field. This keeps every assertion in exactly one of the four buckets — as the classification system requires — while not hiding the minority case.

4. **Internal validation is mandatory and mechanical.** For every template, `supported + computed + fallback + disclosed-missing` must equal the template's total assertion count, with no assertion left uncategorized and no assertion counted in more than one bucket. This is verified programmatically in `audit/truthfulness-matrix.json`'s `validation` array on every run — not asserted by hand.

5. **Corrections to prior phases are recorded, not silently applied.** Where Phase 1C source verification contradicted a Phase 1B finding (e.g. `audit/knowledge-dependencies.json` had attributed `compare-name-country-pair-page` to `data/country-differentials.json`, but the generator was found to never read that file), the correction is documented in the Phase 1C output and report rather than rewritten into the Phase 1B file, preserving each phase's own audit trail.

## The seven artifacts

| # | File | Contents |
| --- | --- | --- |
| 1 | `audit/truthfulness-matrix.json` | Every (template, assertion) pair, one classification each, plus the internal validation check. |
| 2 | `audit/page-truthfulness.json` | Per-template tallies and the truthfulness ratio: `(supported + computed) / all assertions`. |
| 3 | `audit/fallback-taxonomy.json` | The permanent, growing catalog of fallback/disclosure mechanisms — a direct view of `FALLBACK_MARKERS`. |
| 4 | `audit/assertion-catalog.json` | The same assertions, grouped by claim concept instead of by template. |
| 5 | `audit/truthfulness-hotspots.json` | Per-template counts sorted descending by fallback rate. |
| 6 | `audit/truthfulness-report.md` | Human-readable narrative synthesizing 1–5. Purely descriptive. |
| 7 | `scripts/audit/run-truthfulness.js` | Orchestrates 1–6 in dependency order. |

## Scope boundary (read-only)

This phase may only read from and write to:
- **Read:** anywhere in the repository (source code, data, generated HTML, prior `/audit/*.json` reports).
- **Write:** `scripts/audit/**`, `audit/**`, `docs/**` only.

It may never modify `data/**`, `build/**`, `templates/**`, any `scripts/generate-*` or `scripts/build-*` script, any generated HTML/CSS/JS, or `package.json`. Every write path in `scripts/audit/_lib.js` (`writeAuditJson`, `writeAuditText`) enforces this by construction — they refuse to write outside `audit/`.

## Limitations

- **Sibling-batch reconstruction.** The true 150-name "sibling harmony" batch is selected by a live popularity ranking, but the committed `data/popularity.json` only has ranking data for 5 names. Which exact 150 names the real batch contains cannot be reconstructed from committed data, so any assertion whose truth-value depends on batch membership (e.g. the popularity-band scoring factor) has its *mechanism* verified from source but not its *exact page count*. This is reported as a stated limitation next to the figure, not silently estimated, and not modeled as a fifth classification state.
- **Coarse markers.** Some fallback markers (e.g. a bare `—` in a Quick Facts table) can also match unrelated empty fields elsewhere on the same page, making their page count an upper bound rather than an exact isolation of one specific assertion. This is noted per-marker in `audit/fallback-taxonomy.json`.
- **Not every template received the same verification depth.** Templates with many pages and complex generator logic (`name-detail-page`, `names-like-page`, `sibling-harmony-page`, `compare-name-country-pair-page`, `surname-compatibility-page`) were verified against actual rendered HTML. Smaller, simpler list templates (`names-country-page`, `names-style-page`, `popularity-year-page`, `trend-page`) were verified against generator source and, where available, Phase 1B's coverage data, but not independently re-scanned page-by-page in this pass. Where this shallower verification applies, it is stated explicitly in that assertion's `note` field rather than presented with false precision.

## How to extend this system

- **A newly discovered fallback mechanism** (in any future phase, or a future site change): add one entry to `FALLBACK_MARKERS` in `scripts/audit/knowledge-lib.js`. `audit/empty-knowledge.json` (Phase 1B) and `audit/fallback-taxonomy.json` / `audit/truthfulness-matrix.json` (Phase 1C) all pick it up automatically on their next run — no other file needs to change.
- **A newly discovered assertion** (a rendering mechanism not yet cataloged): add one entry to the `buildAssertions()` array in `scripts/audit/truthfulness-lib.js`, with a `state` from the four above and an `evidence.method` describing how it was verified.
- **A new template**: add its assertions to `truthfulness-lib.js`; the matrix, page-truthfulness, hotspots, and catalog scripts require no changes, since they all derive their output from `buildAssertions()`.
